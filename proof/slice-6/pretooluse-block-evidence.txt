The PreToolUse hook is exercised by 14 unit tests — each builds a real
hook callback (the same callback `spawnWorkflowStage` injects into the
SDK) and feeds it a synthetic SDK PreToolUse input. The hook's return
value determines whether the SDK would be allowed to proceed.

Two enforcement classes:

  1. PATH-GATED — Edit, Write, MultiEdit, NotebookEdit. Allowed only
     when the target file is inside the stage's allowed_paths set
     (exact-file match OR directory-prefix match with trailing /).
     Outside that set: blocked.

  2. UNCONDITIONAL — Bash. Workflow-stage main thread cannot shell
     out, full stop. Specialists run tests/builds/etc. via mission
     dispatch (the orchestrating stage SPAWNS a sub-agent / mission
     task and that sub-process owns Bash). This closes the gap Codex
     flagged in review: previously a stage could call
     `bash -c "cat > file"` to write around the Edit/Write gate.

Read-only tools (Read, Grep, Glob, Task, etc.) are NOT in the matcher
list at all — the hook callback is never invoked for them, so the SDK
proceeds normally. Tested explicitly so the boundary stays asserted.

When the hook returns { decision: 'block', hookSpecificOutput: {
permissionDecision: 'deny' } }, the SDK refuses to invoke the tool.
The blocks array passed into buildDenyEditHook captures each block
decision so the workflow runner can record evidence to the run record.

Per the saved Claude Code docs at
/Volumes/4TB-990/dev/files/context/agent-teams/claude-docs/hooks.md,
this is the exit-2 hard-block primitive (in-process equivalent: the
SDK respects decision='block' the same way a CLI hook returning exit
code 2 does). The block fires BEFORE tool execution, non-overridable.
